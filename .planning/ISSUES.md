# ISSUES — NEUROGLYPHS (Concept v2)

Задачи под GitHub: `https://github.com/Ilyaworks/neuroglyphs`.
Полный дизайн: `.planning/CONCEPT.md`. Референс картинки: 13 кадров, цель — воспроизвести их.

**Правило дробления:** одна задача = один issue = одна сессия = один новый файл размером
до 150 строк. Если задача не влезает в один файл — она разбита на подзадачи с буквами
(`N12a`, `N12b`). Сессия может сжиматься по контексту, поэтому в задаче всегда указан
точный список файлов для чтения — читать что-то ещё запрещено.

**Проверка картинки.** С задачи `N11`, когда на экране появляется мир, `finish-task`
прогоняет страницу с флагом `--expect-content`: чёрный или почти чёрный кадр считается
провалом, даже если ошибок в консоли нет. Инструмент печатает долю светящихся пикселей,
среднюю яркость, число оттенков и кадры в секунду — эти числа попадают в отчёт
проверяющему. Для задач с пульсацией есть `--expect-motion`: два кадра с разницей
в 1.4 секунды не должны быть побайтово одинаковыми.

## Правила для исполнителя (вставлять в каждую сессию)

1. Не составляй план. Первым действием создавай файл.
2. Один новый файл за сессию. Правки существующих файлов разрешены только там, где задача
   прямо говорит, какой файл и сколько строк.
3. Читай только перечисленные файлы. Ничего больше не открывать.
4. Никакого `Math.random()` в генерации — только сеяный PRNG из `src/core/rng.js`.
5. Все визуалы — глифы, точки, линии, шейдеры на глиф-геометрии. Других ассетов нет.
6. Никакого текста как интерфейса внутри мира: задачи сообщаются цветом, пульсацией,
   частотой. Формулы и надписи — декор.
7. Тот же сид = тот же мир побайтово. Задача, добавляющая параметр, добавляет и проверку.
8. Пороги в инструментах проверки менять запрещено. Не проходит — значит не готово.
9. В конце — одна команда проверки из задачи и явный STOP с отчётом.

# Дорожная карта

Шесть демо-точек. В каждой есть что показать на экране; между ними ничего не «висит
недоделанным».

| Демо | Что видно | Задачи | Штук | Сессий |
|---|---|---|---|---|
| **D1 — Первый мир** | Летаешь по миру из глифов, восемь типов структур, туман, светящийся портал выхода | N01–N21 | 21 | 24–28 |
| **D2 — Картинка как на референсе** | Свечение, дисторсии, зеркальный пол, палитры настроений, 64 формы, формулы | N22–N31 | 10 | 12–14 |
| **D3 — Музыка = сердцебиение** | Мир пульсирует под твой трек, BPM и тональность, дрон по умолчанию | N32–N40 | 9 | 10–12 |
| **D4 — Сбор и прогресс** | 128 вещей в мире, счётчик `042 / 128`, близость выхода, собранное меняет сид | N41–N46 | 6 | 7–9 |
| **D5 — Бесконечность** | Переход между мирами, курированные сиды, меню, world book, шаринг кода | N47–N52 | 6 | 7–9 |
| **D6 — Атмосфера и полировка** | Дыхание, созвездия, эхо, моире, задачи без текста, настройки качества | N53–N62 | 10 | 11–13 |

Итого 62 задачи, порядка 75 сессий модели с учётом повторных попыток. Одна проверка с моей
стороны на задачу.

**Когда демо актуально показывать:**

- **D1** — первая точка, где проект перестаёт быть заготовкой: есть мир, есть полёт, есть
  выход. Показывать, чтобы решить, та ли это геометрия.
- **D2** — точка сравнения с референсом. Здесь кладём скриншот рядом с кадром и решаем,
  добираем ли ещё картинку или идём дальше. Это самая важная демо-точка проекта.
- **D3** — точка, где становится понятно ядро идеи: без музыки калейдоскоп мёртвый.
- **D4** — первая точка с геймплеем: сбор и прогресс.
- **D5** — точка, где игра становится бесконечной, а не одним миром.
- **D6** — то, что делает миры разными по ощущению, а не по геометрии.

Критический путь до первой картинки: `N01 → N02 → N03 → N05 → N06 → N07 → N09 → N10 → N11`
— девять задач, после них на экране уже светящееся глифовое поле по коду сида.

Дальше до D2 добираются `N12 → N13 → N14 → N16` (структуры), `N22 → N25 → N26` (свечение
и палитры), `N27 → N28` (формы), `N29` (пол). Тесты (`N04`, `N08`, `N15`) можно двигать, но
не откладывать за пределы своей демо-точки: без них детерминизм перестаёт проверяться.

Идут параллельно и не блокируют картинку: движение (`N19`, `N20`), музыка (`N32`–`N37`),
формулы (`N30`).

## N03 — Сеяный PRNG

**Файлы:** создать `src/core/rng.js`
**Читать:** —
**Метки:** `area:core`, `epic:D1`

- `mulberry32(seedInt)` → функция без аргументов, `[0, 1)`.
- `strToSeed(str)` → 32-битное целое из строки (FNV-1a).
- `hash32(n)` → `[0, 1)`, реализация строго splitmix32:
  ```js
  let x = (n + 0x9e3779b9) >>> 0;
  x ^= x >>> 16; x = Math.imul(x, 0x21f0aaad) >>> 0;
  x ^= x >>> 15; x = Math.imul(x, 0x735a2d97) >>> 0;
  x ^= x >>> 15;
  return (x >>> 0) / 4294967296;
  ```

Хеш на одном сдвиге брать нельзя: замером получено, что он даёт корреляцию соседних
значений −0.42 и заполненность объёма 0.085 против 0.77 у splitmix32 — точки слипаются
в комок, и все формы выходят вырожденными.

**Проверка:** `node -e "import('./src/core/rng.js').then(m=>console.log(m.hash32(1).toFixed(4)))"`
— печатает число между 0 и 1.

## N07 — Кодек сида

**Файлы:** создать `src/core/seed.js`
**Читать:** `src/core/rng.js`
**Метки:** `area:core`, `epic:D1`

Сид — строка base36 в формате `XXXX-XXXX-XXXX`. Битовая упаковка. Заложить все поля сразу,
даже те, что заполнятся позже:

| поле | биты | что задаёт |
|---|---|---|
| `structure` | 3 | тип структуры, 0–7 |
| `palette` | 3 | палитра |
| `mood` | 3 | настроение, 0–5 |
| `density` | 4 | плотность частиц |
| `fractal` | 3 | фрактальная глубина |
| `motion` | 3 | паттерн движения |
| `nonEuclid` | 3 | неевклидовы параметры |
| `music` | 4 | параметры музыки |
| `shape` | 6 | форма глифового поля |
| `exit` | 8 | комбинация выхода |

Экспорт: `encodeSeed(fields)`, `decodeSeed(code)` → поля плюс `rng`, `randomSeed(rng)`,
`SEED_FIELDS`. Неверный код возвращает `null`, а не бросает исключение.

Суммарно поля занимают 40 бит, поэтому упаковывать через `BigInt`: обычные побитовые
операции в JS работают на 32 битах и потеряют старшие поля.

**Инварианты кодека:**

- `decodeSeed(encodeSeed(f))` возвращает те же поля.
- **Код канонический:** `encodeSeed(decodeSeed(code)) === code` для любого кода, который
  `decodeSeed` принял. Отсюда два требования. Первое: коды со значением больше 2^40
  отвергать через `null`, а не маскировать лишние старшие биты — иначе у одного мира
  появляются коды-синонимы (`ffff-ffff-ffff` и `0000-8cng-bh0b` дают одни и те же поля).
  Второе: `rng` выводить из упакованного числа, а не из текста кода — иначе два написания
  одного мира дают разную геометрию деталей, и мир, пересохранённый в world book,
  перестаёт совпадать с присланным по ссылке.
- **`rng` зависит от всех 40 бит.** `Number(packed % 2^32)` отбрасывает старшие восемь бит,
  то есть поле `exit`, и тогда 256 миров получают одинаковую геометрию, различаясь лишь
  замком портала. Мешать целиком, например
  `mulberry32(Number(packed & 0xffffffffn) ^ Number(packed >> 32n))`. Это важно из-за
  механики сбора: вещи складываются в сид, и изменение только `exit` обязано давать другой
  мир, а не тот же самый.
- Верхний регистр принимать и приводить к нижнему: кодами делятся копипастой.

**Проверка:** `node --check src/core/seed.js` — молча.

## N18 — Портал в мире и близость к нему

**Файлы:** правка `src/world/world.js` (до 30 строк)
**Читать:** `src/world/world.js`, `src/world/portal.js`
**Метки:** `area:world`, `epic:D1`

Мир добавляет ровно один портал, пишет его позицию в `userData.exitPosition` и отдаёт
`distanceToExit(cameraPos)` — понадобится HUD-у.

Три вещи, на которых эта задача провалится, если о них не знать (лимит поднят с 20 до
30 строк именно под них):

1. **Камера смотрит в другую сторону.** `boot.js` создаёт `PerspectiveCamera` и не
   двигает её: она стоит в начале координат и смотрит в −Z. `buildExitPortal` возвращает
   `position` с `z = +120`, то есть за спиной наблюдателя. Портал надо ставить перед
   камерой и внутри габарита мира: брать `group.userData.bounds` (его пишет `N16`) и
   сажать выход на дальнюю по −Z границу, а не на константу.
2. **`world-check` требует, чтобы каждое облако точек было видно** — не меньше 20
   пикселей вклада при гашении. Портал приносит в сцену два новых облака, рамку и
   контур. Облако вне кадра даёт ноль, и задача не закроется. На `N16` это уже стоило
   одной итерации: дальний план давал 17 пикселей при пороге 20.
3. **Пульсация и очистка.** Портал строит свои материалы, поэтому подшей его к общим
   uniform-ам поля, как это сделано со звёздами: `uPulse` и `uTime` брать те же самые
   (`portal.uniforms` возвращается наружу). И освободи геометрии с материалами портала
   в `dispose()` — сейчас там перечислено только своё.

## N19 — Fly-cam

**Файлы:** создать `src/player/flycam.js`
**Читать:** `src/boot.js`
**Метки:** `area:gameplay`, `epic:D1`

`createFlyCam(camera, dom)` → `{ update(dt), setSpeed(v), dispose() }`. WASD плюс мышь
через pointer lock, `Shift` ускорение, `Ctrl` замедление, `Space` и `C` вверх-вниз. Разгон
и торможение плавные, экспоненциальным сглаживанием. Коллизий и гравитации нет. Потеря
фокуса окна не должна «уносить» камеру.

На эту задачу заведён гейт `node tools/flycam-check.mjs`: он грузит модуль в странице,
шлёт настоящие события клавиатуры и смотрит, куда уехала камера. Что он требует —
чтобы это не выяснилось из провала:

- Клавиши читаются по `event.code`: `KeyW`, `KeyS`, `KeyA`, `KeyD`, `Space`, `KeyC`,
  `ShiftLeft`/`ShiftRight`, `ControlLeft`/`ControlRight`. События шлются на
  `document.body` всплывающими, поэтому слушать можно на `window`, `document` или `dom`.
- `update(dt)` принимает секунды. За 30 кадров по 1/60 c камера обязана пройти не
  меньше 5 единиц, и движение вперёд — это уменьшение `z` у камеры без поворота.
- `Shift` удлиняет путь минимум в 1.5 раза, `Ctrl` укорачивает минимум на пятую часть,
  `setSpeed(240)` при базовой скорости даёт путь минимум вдвое длиннее.
- Плавность: первый кадр разгона не длиннее 0.6 от установившегося. После отпускания
  выбег обязан быть ненулевым, а через 50 кадров камера обязана встать — остаточный
  ход не больше 2% от разгона.
- `window` получает `blur` с зажатой `W`: камера обязана встать. Это и есть «не уносит».
- После `dispose()` клавиши камеру не двигают вовсе.
- `update()` не падает и не рождает `NaN` на `dt`, равном 0, отрицательном, `NaN`,
  `undefined` и очень большом.
- `Math.random()` в файле запрещён — правило 4.

Пороги в `tools/flycam-check.mjs` не менять.

**Проверка:** `node tools/flycam-check.mjs` — печатает `FLYCAM_OK`.

# Правки по ревью

Мелкие исправления, найденные проверяющим при чтении кода. Каждая — одна-две строки,
делаются по указанию в сообщении проверяющего, не занимают отдельную демо-точку.

## R1 — ограничить dt сверху

**Файлы:** правка `src/boot.js` (одна строка)

`dt` считается как разница времени между кадрами. Когда вкладка уходит в фон,
`requestAnimationFrame` останавливается, и первый кадр после возврата даёт `dt` в десятки
секунд — всё, что двигается от `dt`, прыгает разом. Ограничить: `Math.min(dt, 0.1)`.

**Проверка:** `node --check src/boot.js` — молча.

## R2 — запретить кэширование в dev-сервере

**Файлы:** правка `server.mjs` (одна строка)

Добавить в заголовки ответа `'Cache-Control': 'no-store'`. Иначе браузер отдаёт старую
версию модуля из кэша, и проверка идёт не по тому коду, что на диске.

**Проверка:** `node tools/check-server.mjs` — печатает `SERVER_OK`.

## R3 — починить проверку выхода за корень

**Файлы:** правка `server.mjs` (одна строка)

`filePath.startsWith(ROOT)` истинно и для соседней папки `C:
euroglyphs-secret`, потому
что сравнение идёт без разделителя. Сравнивать с `ROOT + path.sep`, сам `ROOT` разрешать
отдельно.

**Проверка:** `node tools/check-server.mjs` — печатает `SERVER_OK`.

## R4 — пережить потерю WebGL-контекста (к демо-точке D6)

**Файлы:** правка `src/boot.js`

Подписаться на `webglcontextlost` и `webglcontextrestored` на канвасе: при потере
остановить цикл и вызвать `event.preventDefault()`, при восстановлении пересобрать
ресурсы. Без этого долгая сессия однажды остаётся с чёрным экраном навсегда.

**Проверка:** `node --check src/boot.js` — молча.

## R5 — сид: проверять длину групп, иначе код неканоничен

**Файлы:** правка `src/core/seed.js` (одна строка), правка `test/seed.test.mjs` (дописать
случаи в пункт 3)

`decodeSeed` склеивает группы и проверяет результат целиком: `parts.join("")` плюс
`/^[0-9a-z]{12}$/`. Поэтому любое разбиение на три группы суммой 12 символов проходит:

```
decodeSeed("00-00000000-00")  → принят, encodeSeed(...) === "0000-0000-0000"
decodeSeed("000-00000-0000")  → принят, encodeSeed(...) === "0000-0000-0000"
decodeSeed("0-0-0000000000")  → принят, encodeSeed(...) === "0000-0000-0000"
```

Это нарушает инвариант каноничности из `N07`: `encodeSeed(decodeSeed(code)) === code` для
любого кода, который `decodeSeed` принял. Тот же дефект, что и коды-синонимы выше 2^40,
только с другой стороны: один мир получает несколько написаний, и в world book (`D5`) он
ляжет двумя записями, а ссылка и пересохранение разойдутся.

Проверять формат до склейки: `/^[0-9a-z]{4}-[0-9a-z]{4}-[0-9a-z]{4}$/` по строке после
`toLowerCase()`. Пункт 3 теста дополнить всеми тремя кодами выше — без этого правка
не закрыта воротами.

**Проверка:** `npm test` — печатает `RNG_OK` и `SEED_OK`.

## R7 — геометрия поля: импорт three и незаполненные атрибуты

**Файлы:** правка `src/world/fieldGeometry.js`

`N09` закрылась неработающим модулем: `node --check` проверяет только синтаксис, а
`browser-check` файл не видит, потому что до `N11` его никто не импортирует. Четыре
дефекта, все проверены прогоном.

**1. `THREE` не импортирован.** Модуль пользуется `THREE.BufferGeometry`, но импорта нет,
а в ES-модуле `THREE` не глобальный:

```

```

Добавить `import * as THREE from "three";` — как в `src/boot.js` и `src/core/atlas.js`.

**2. `glyph`, `size`, `offset` только выделены, но никогда не заполняются.** Все три
остаются нулями. Значит каждая точка — глиф с индексом 0 размера 0, то есть на экране
не будет ничего, и `N11` упрётся в чёрный кадр. `src/core/rng.js`, который задача велела
прочитать, в модуле не используется вовсе — читать его велели именно за этим. Заполнять

```js
glyphs[i] = Math.floor(hash32(i * 3 + 1) * 128);   // 0..127, индекс клетки атласа
sizes[i]  = 0.6 + hash32(i * 3 + 2) * 1.4;         // 0.6..2.0, множитель, никогда не 0
offsets[i] = hash32(i * 3 + 3);                    // 0..1, фаза пульсации
```

`hash32` зависит только от индекса, поэтому инвариант «тот же сид = тот же мир побайтово»

`N27`/`N28`.

**3. `boundingSphere` не считается.** Наполнение асинхронное, поэтому three посчитает сферу
сам при первом кадре — по ещё нулевым координатам, получит радиус около нуля и отсечёт всё
облако отсечением по пирамиде видимости. Звать `geometry.computeBoundingSphere()` в конце
каждого чанка.

**4. `ready` не отклоняется.** Если `fill` бросит исключение, промис не осядет никогда,
и `N11`, который его ждёт, повиснет с чёрным экраном без единой ошибки в консоли.
Обернуть тело чанка в `try/catch` и в `catch` звать `reject`.

Порог чанка 20 000 не менять: `geometry-check` считает вызовы `requestAnimationFrame`
и требует не меньше `ceil(count / 20000)`.

**Проверка:** `node tools/geometry-check.mjs` — печатает `GEOMETRY_OK`.

выбора задачи и не зовёт её для правок `R`, чтобы это не повторялось.

Принято с отклонениями, оба проверены и оставлены:

- Заполнение идёт от одного экземпляра `mulberry32(0x9e3779b9)`, а не от `hash32(i)`.

- `size` заполняется в диапазоне 1..10, а не 0.6..2.0, как было предписано. Разброс

Мелочи, править отдельно не стоит: `needsUpdate` у `glyph`, `size` и `offset` ставится

сохранён; плавность появления при желании чинится на `N11`.

## R8 — шейдер поля: выборка атласа по gl_PointCoord

**Файлы:** правка `src/world/fieldMaterial.js`

Шейдер компилируется (программа собирается, ошибок в консоли нет) и не рисует ничего.
Замер настоящим рендером, по одной точке на глиф, спрайт 64px:

```
глиф   0: светящихся пикселей 0
глиф   3: светящихся пикселей 0
глиф  20: светящихся пикселей 0
глиф  64: светящихся пикселей 0
глиф 100: светящихся пикселей 0
```

Причина: `vUv` считается в вершинном шейдере, а у точки один вершинный вызов на весь
спрайт. Значит `texture2D(uAtlas, vUv)` берёт **один и тот же тексель для всех пикселей
точки** — форма глифа не может появиться в принципе. А поскольку рядом стоит
`if (alpha < 0.01) discard;`, и этот единственный тексель приходится на угол клетки, где
у центрированного глифа прозрачно, то отбрасывается вся точка целиком. Отсюда пустой
экран, а не квадраты.

Выборка обязана идти по `gl_PointCoord` — это координата пикселя внутри спрайта, от
`(0,0)` до `(1,1)`, и она есть только во фрагментном шейдере. То есть из вершинного
шейдера надо передавать индекс глифа (`varying float vGlyph`), а границы клетки и саму
выборку считать во фрагментном:

```glsl
vec2 uv = vec2(mix(u0, u1, gl_PointCoord.x), mix(v1, v0, gl_PointCoord.y));
```

Границы клетки брать как в `atlas.uv()`: `u0 = (c + pad)/16`, `u1 = (c + 1 - pad)/16`,
`v0 = 1 - (r + 1 - pad)/8`, `v1 = 1 - (r + pad)/8`, где `pad = 0.5/64`. `v` перевёрнут
потому, что у `CanvasTexture` включён `flipY`, а `gl_PointCoord.y` растёт сверху вниз —
поэтому по `y` идёт `mix(v1, v0, ...)`, а не наоборот.

Заодно: `floor(r + 1.0 - pad)` в текущем коде обнуляет весь смысл `pad`, потому что
`pad` меньше единицы и `floor` его съедает. В новой выборке этой строки не будет.

Что оставить как есть: зажим `min(computed, 64.0)`, `AdditiveBlending`, `depthWrite`
`false`, `depthTest` `true`, `transparent` `true`, набор uniform-ов — всё это инструмент
проверяет и всё это уже правильно.

Если не сходится — рядом лежит `tools/fixture-material.js`: эталонный материал, на
котором инструмент проверялся, там та же выборка целиком. Это служебный файл проверки,
импортировать его из `src/` нельзя, но сверяться с ним можно.

**Проверка:** `node tools/material-check.mjs` — печатает `MATERIAL_OK`. На эталоне
инструмент даёт 5 спрайтов с формой из 5, заливка габарита 0.32–0.58 при пороге 0.90.

## R9 — туман в шейдере и видимость дальнего поля

**Файлы:** правка `src/world/fieldMaterial.js`, правка `src/world/world.js`

`N11` ставит `scene.fog = new THREE.FogExp2(...)`, но на сырой `ShaderMaterial` это не
действует: three подмешивает туман только в свои материалы либо когда шейдер сам включает
вставки тумана. В `fieldMaterial.js` нет ни `fog: true`, ни `fog_pars_fragment`, ни
собственного затухания — значит дальние глифы не тускнеют совсем. Замер: обнуление
плотности тумана не меняет кадр ни на один пиксель.

```
кадр с туманом:  светится 4032 пикселей, средняя яркость 16.186
кадр без тумана: светится 4032 пикселей, средняя яркость 16.186
```

Это признак 2 из `REFERENCE.md` для `D1`: «глубина читается, дальние глифы тусклее».
На скриншоте `n11.png` его и не видно — поле выглядит плоским шумом.

**Как чинить.** Вставки тумана от three тут не годятся: их `fog_fragment` смешивает цвет
с `fogColor`, а при `AdditiveBlending` подмешивание серого поднимет чёрный фон до серого,
что `REFERENCE.md` прямо запрещает. Поэтому затухание своё, к чёрному:

- в `fieldMaterial.js` добавить `uniform float uFogDensity` со значением
  `opts.fogDensity ?? 0.0011` — `opts` в сигнатуре уже есть и пока не используется;
- передать глубину из вершинного шейдера: `varying float vDepth;` и `vDepth = -mvPosition.z;`
- во фрагментном умножить цвет на прозрачность тумана по формуле `FogExp2`:

```glsl
float f = 1.0 - exp(-uFogDensity * uFogDensity * vDepth * vDepth);
gl_FragColor = vec4(vColor * (0.8 + 0.4 * uPulse) * (1.0 - f), texel.a);
```

**Дальнее поле при этом надо спасти.** На радиусе 2200 та же формула даёт `f = 0.997`,
то есть «звёзды» исчезнут полностью. И они и сейчас невидимы по другой причине: размер
точки считается как `size * 300 / depth`, при `size` 1..4 и глубине 2200 это 0.14..0.55
пикселя, то есть меньше пикселя. Поэтому в `world.js`:

- строить материал звёзд как `buildFieldMaterial(atlas, { fogDensity: 0 })` — дальний
  план не должен съедаться туманом, он и есть фон;
- поднять их размер до `starSize[i] = 6 + rng() * 12;` — при глубине 2200 это даёт
  1.0..3.1 пикселя, то есть точки наконец видно;
- связать пульсацию: сейчас `createWorld` возвращает uniform-ы только основного поля,
  поэтому звёзды не пульсируют вовсе. После создания второго материала добавить
  `starMat.uniforms.uPulse = uniforms.uPulse;` и `starMat.uniforms.uTime = uniforms.uTime;`
  — один объект на два материала, и одна запись из `boot.js` двигает оба.

Порог инструмента не менять: он требует, чтобы обнуление плотности поднимало среднюю
яркость минимум в 1.15 раза. На правильной реализации замерено 1.412.

**Проверка:** `node tools/world-check.mjs` — печатает `WORLD_OK`.

## R10 — раскладки: наполнять мир на заданное число точек

**Файлы:** правка `src/world/layouts/architectural.js`

Ни одна из трёх раскладок не может наполнить мир. Поле берёт плотность из сида, это
1500–31500 точек, а раскладки при своих значениях по умолчанию дают:

```
layoutFractalCorridors   260 точек
layoutCrystalline       2582 точки
layoutGeometric          212 точек
```

Само по себе это ещё не приговор — параметры на то и есть. Но у коридоров **ручки
плотности нет вовсе**, и это уже дефект:

```
depth 2 -> 156      depth 5 -> 788        radius 200 -> 136
depth 3 -> 240      depth 6 -> 1020       radius 20  -> 248
depth 4 -> 380                            corridorLength 600 -> 360
```

`depth 6` — это 63 коридора при экспоненциальном ветвлении, и всё равно 1020 точек.
Причина в `emitCorridor`: `spacing = radius * (0.8 + rng() * 0.6)`, то есть шаг глифов
пропорционален радиусу. Поэтому стена любого размера всегда получает примерно
`3 x 2` точки, и увеличение масштаба плотности не добавляет. Кристаллы и сетка
масштабируются нормально (`count 800` → 25199, `grid 50` → 28920), но и они не знают,
сколько точек у них просят.

**Контракт.** Каждая раскладка принимает `params.target` — сколько точек нужно, по
умолчанию 20000 — и возвращает столько же с допуском 30%. Инструмент проверяет это на
5000 и на 20000.

- `layoutGeometric`: считать сетку из цели, а не брать 9.
  `grid = Math.max(4, Math.round(Math.cbrt(target / occupancy)) - 1)`. При `occupancy`
  0.22 и цели 20000 это даёт `grid` 44 и около 20000 точек.
- `layoutCrystalline`: один кристалл даёт около 32 точек при текущих настройках, значит
  `count = Math.max(1, Math.round(target / 32))`. Цель 20000 → 625 кристаллов.
- `layoutFractalCorridors`: нужна настоящая ручка шага. Собрать дерево коридоров
  сначала в список (`origin`, `dir`, `length`, `radius`), посчитать суммарную площадь
  стен `Σ 4 * length * (radius * 2.2)`, и только потом взять шаг
  `spacing = Math.sqrt(totalArea / target)`, с ним и рисовать. Тогда плотность стен
  задаётся целью, а не радиусом. Разброс шага от `rng` оставить, но как множитель
  вокруг этого значения, не вместо него.

Порог 30% в инструменте не менять. На эталоне `tools/fixture-layouts/reference.js`
замерено отклонение 6% на цели 5000 и 0% на 20000 — значит контракт выполним.

**Заодно, мелочи в том же файле.** `import { mulberry32 }` в первой строке не
используется вовсе: `rng` приходит аргументом. У `orthonormal(rng, base)` первый
параметр не используется. В `emitGlyphRing` есть слагаемые `axis[0] * 0` — умножение
на ноль. Убрать, раз всё равно правишь файл.

## R11 — коридоры: держать цель на любом сиде, а не в среднем

**Файлы:** правка `src/world/layouts/architectural.js`

`R10` принята для `layoutCrystalline` и `layoutGeometric`: на 24 сидах и четырёх целях
их худшее отклонение 7% и 8%. `layoutFractalCorridors` держит цель только в среднем.
Медиана 8–14%, но хвост уходит далеко:

```
цель  1500: допуск нарушен на 4 сидах из 24, худший дал 2192 вместо 1500  (46%)
цель  5000: нарушен на 4 из 24, худший дал 3180 вместо 5000               (36%)
цель 20000: нарушен на 1 из 24, худший дал 13480 вместо 20000             (33%)
цель 31500: нарушен на 2 из 24, худший дал 21156 вместо 31500             (33%)
```

Причина в том, что `spacing = Math.sqrt(totalArea / target)` считает площадь, а точки
кладутся по целой сетке. Каждая стена выдаёт `(floor(length / spacing) + 1) * (floor(height / spacing) + 1)`:
единицы дают систематический излишек, растущий с числом стен, а `floor` наоборот теряет.
Что перевесит — зависит от формы дерева, то есть от сида. Плюс разброс шага от `rng`,
оставленный множителем вокруг `spacing`, делает предсказание площади ещё менее связанным
с тем, сколько точек выйдет на самом деле.

**Как чинить.** Дерево коридоров уже собирается в список первым проходом, а значит число
точек при данном шаге — чистая функция, и её можно решить точно, без угадывания:

```js
const predict = (s) => walls.reduce(
  (n, w) => n + (Math.floor(w.length / s) + 1) * (Math.floor(w.height / s) + 1), 0);

let lo = 0.5, hi = 500;
for (let i = 0; i < 40; i++) {
  const mid = (lo + hi) / 2;
  if (predict(mid) > target) lo = mid; else hi = mid;   // точек тем меньше, чем больше шаг
}
const spacing = hi;
```

Два условия, без которых это не сработает:

- **Шаг больше не умножать на `rng`.** Иначе предсказание не совпадает с эмиссией, и
  всё возвращается к угадыванию. Разброс от сида оставить, но на координатах точек
  (дрожание вокруг узла сетки), а не на числе шагов.
- **Кольца на концах коридоров учесть.** Каждый коридор кладёт ещё 16 точек кольцом:
  либо включить их в `predict`, либо вычесть `16 * количество коридоров` из цели до
  подбора шага.

Порог 30% и список сидов в инструменте не менять. На эталоне
`tools/fixture-layouts/reference.js` худшее отклонение по 24 сидам — 3%, значит держать
цель на любом сиде выполнимо.

**Проверка:** `node tools/layout-check.mjs` — печатает `LAYOUT_OK`.

**Закрыта и проверена шире гейта.** На 300 сидах с другой решётки (`104729 + i * 1013`,

## R12 — раскладки: слушаться extent, размер не от плотности

**Файлы:** правка `src/world/layouts/organic.js`, правка `src/world/layouts/architectural.js`

Контракт по числу точек все шесть раскладок держат: отклонение 0–2%. А вот размера
у них нет — и это мой пробел, я его не задал, когда писал `R10`. Замер:

```
                      extent 200   extent 400   при удвоении   габарит по целям 1500..31500
layoutCrystalline            217          217        x1.00      201/217/217/217
layoutFractalCorridors       291          291        x1.00      293/289/293/291
layoutGeometric              100          201        x2.00      151/151/151/150
layoutAlmostReal              67           67        x1.00       39/45/61/67
layoutOrganic                190          190        x1.00      186/190/190/190
layoutVoid                   149          283        x1.90      770/762/761/620
```

Четыре раскладки параметр размера не слушают вовсе. `layoutGeometric` слушает, но
считает `extent` стороной куба, а не радиусом, поэтому даёт вдвое меньше заказанного.
`layoutVoid` слушает, но расползается на 620–770 при мире радиусом 400 — там туман
съедает почти всё. А `layoutAlmostReal` вдобавок **меняет размер от числа точек**:
39 единиц при цели 1500 и 67 при 31500. То есть в мире с малой плотностью аркада
съёживается в комок вокруг камеры.

**Контракт размера.** `params.extent` — радиус объёма, который надо заполнить, то есть
максимальное удаление точки от центра; по умолчанию 400, как радиус поля в `world.js`.
Сторона куба, если раскладка думает кубами, вдвое больше.

- Габарит от центра обязан лежать в полосе 0.6–1.5 от `extent`.
- При удвоении `extent` габарит обязан удвоиться (допуск 1.5–2.5 раза). Попадание в
  полосу без слежения не считается: у `layoutFractalCorridors` фиксированные 291 попали
  в допуск и при 200, и при 400 — чистая случайность.
- `target` задаёт **плотность, а не размер**: по целям от 1500 до 31500 габарит не
  должен разъезжаться больше чем на 15%.

**Как чинить.** Правило одно на все шесть: каждая внутренняя константа размера
выражается долей от `extent`, а не числом. `corridorLength`, радиус трубы коридора,
радиус разброса кристаллов, шаг сетки, размер аркады, разлёт пустоты — всё от `extent`.
Числа не угадывать: `layout-check` печатает и габарит, и множитель слежения, и разброс
по целям — подгонять по его выводу.

Отдельно у `layoutAlmostReal`: цель обязана добавлять **плотность внутри того же
объёма** — больше колонн и ступеней на ту же аркаду или больше аркад в том же
объёме, — а не раздувать объём.

Полосы 0.6–1.5, 1.5–2.5 и 15% в инструменте не менять. На эталоне
`tools/fixture-layouts/reference.js` замерено: габарит 1.00 от заказанного на обоих
`extent`, слежение ровно 2.00, разброс по целям 1%. Контракт выполним.

## R13 — пересечённые миры: две разные структуры, без невидимых точек

**Файлы:** правка `src/world/layouts/twisted.js`

Контракты `N14` держит: цель 0–2%, слежение за `extent` 1.97–2.00, разброс по целям
1–7%, порядок в `LAYOUTS` верный. Два других дефекта.

**1. ID 7 это ID 1, дважды.** `layoutCrossedWorlds` вызывает `emitCrossed` два раза с
одними и теми же `R = extent * 0.5` и `r = extent * 0.2`, различаются только случайная
ось и фаза интерференции. То есть это тот же тор, что и `layoutNonEuclidean`. Профиль
по радиусу совпадает до 0.01 в каждой из восьми оболочек:

```
1 неевклид       0.00 0.00 0.00 0.06 0.14 0.24 0.35 0.21
7 пересечённые   0.00 0.00 0.00 0.06 0.13 0.24 0.35 0.21
```

Расстояние между ними 0.012, между следующей ближайшей парой — 0.260, между самой
далёкой — 1.103. Разрыв в двадцать раз: это близнецы, а не два силуэта из восьми.
Задача просит «две структуры наложены», то есть две **разные** структуры, а не одну
дважды. Это же нужно и признаку 3 из `REFERENCE.md`, и моире из признака 25.

Чинить композицией: выбрать по `rng` две **разные** раскладки, вызвать каждую с целью
`target / 2` и тем же `extent` и склеить. Импортировать при этом
`architectural.js` и `organic.js` напрямую — **не** `index.js`: он сам импортирует
`twisted.js`, получится цикл. Тогда силуэт ID 7 меняется от сида, как и должен, а
интерференция возникает между честно разными структурами.

**2. Двадцать три процента точек не рисуются.** `interference = 0.7 + 0.6 * sin(...)`
даёт множитель от 0.1 до 1.3, и при `baseScale` 4 минимальный `scale` выходит 0.24.

глубине 400 при среднем пульсе это `scale * 0.94` — точка мельче пикселя не рисуется
вовсе. Замер: 23% точек на глубине 400, 8% на глубине 200. У остальных семи раскладок
ноль.

Темнить надо яркостью, а не размером: размер ниже пикселя — это не тусклая точка, а
отсутствующая, и цель при этом просит 20000, а на экран выходит 15400. Пока в шейдере
нет канала яркости на точку, множитель просто ограничить: при `interference` от 0.5
минимальный `scale` выходит `4 * 0.6 * 0.5 = 1.2`, то есть 1.13 пикселя на глубине 400 —
уже видно. Подойдёт `0.75 + 0.25 * Math.sin(...)`.

Настоящее моире яркостью — это признак 25 и демо-точка `D6`; там в шейдер добавится
канал на точку, и тогда к этому можно вернуться.

## R14 — портал выхода: рамка из четырёх сторон и зависимость от сида

**Файлы:** правка `src/world/portal.js`
**Читать:** `src/world/portal.js`, `src/core/seed.js`

Контракт `N17` держит частично: `buildExitPortal` возвращает все пять полей, пять форм
отверстия достижимы и не вырождены, `isSolved` отвергает и подмену любого слота, и
комбо чужого портала, нечисел в атрибутах нет. Четыре дефекта, все ловятся новым гейтом
`node tools/portal-check.mjs`.

**1. Ни один вид вызова не даёт правильный портал.** `code` берётся только из строки,
`exit` — только из объекта:

```js
const code = typeof seed === "string" ? seed : null;
const exit = typeof seed === "object" && seed !== null ? seed.exit : 0;
```

Вызов полями `decodeSeed` (так его позовёт `N18`) даёт `code = null`, то есть поток
`mulberry32(strToSeed("portal:portal"))` — **один и тот же во всех мирах**. Вызов кодом
даёт `exit = 0`, то есть форма всегда четырёхлистник, объект 0, звук 0. Замер на
24 сидах: уникальных рамок 1 из 24, формула принимает 1 значение из 128.

Чинить нормализацией входа: и код, и поля приводить к `exit` (из строки — через
`decodeSeed`, при неразборчивом коде `exit = 0`), поток брать от него:
`mulberry32(strToSeed(exit + ":portal"))`. Тогда `buildExitPortal(код)` и
`buildExitPortal(decodeSeed(код))` дают побайтово один портал — это проверяется.

**2. Рамка не прямоугольная: две стороны из четырёх.** В `rectPerimeter` периметр
посчитан как `2 * (halfW + halfH)`, а обход расписан по сторонам длиной `2*halfW` и
`2*halfH`, то есть на `4 * (halfW + halfH)`. При `halfW = 30, halfH = 18` это 96 против
192: `d` не доходит до третьей и четвёртой ветки, низ и левый бок не рисуются никогда.
Замер: точки лежат в `y` от −14.8 до 18.0 при заявленных ±18, на нижней стороне 3%
точек, на левой 3%, и точек 30 вместо 60 при шаге 3.2.

Это прямо ломает инвариант задачи «выход прямоугольный и есть в каждом мире». Чинить
периметром `4 * (halfW + halfH)`; шаг 3.2 не менять, число точек станет 60.

**3. Формула-слот одинакова во всех мирах.** Следствие дефекта 1, но проверяется
отдельно: `formula` берётся из потока, а поток константный, поэтому во всех 24 мирах
формула равна 9. Один из четырёх слотов загадки не несёт информации. После починки
потока слот обязан меняться — гейт требует не меньше 6 разных значений на 24 сидах.

**4. Контур отверстия нечем анимировать.** Наружу отдан только `barUniforms` рамки, у
контура свой набор `uniforms`, и он никуда не отдан. Рамка и контур будут пульсировать
вразнобой, а `N18` не сможет вести ни то ни другое. Сделать как в `world.js` со
звёздами: один набор `uniforms` на оба облака (`holeMat.uniforms.uPulse = uniforms.uPulse`,
то же для `uTime`) и вернуть его наружу пятым полем `uniforms` рядом с `group`.

Заодно: комментарий «Позиция портала: за дальним краем мира» врёт — `z = 120` лежит
внутри поля радиуса 400. Позицию ставит `N18`, поэтому здесь достаточно поправить
комментарий, а не число.

Пороги в `tools/portal-check.mjs` не менять.
